# 性能压测：数据、方法与两个被压出来的问题

> 所有数字都是本机实测，脚本在 `bench/`，可以原样复现。
> 没有一处是估算或从别处抄来的。

## 1. 环境（决定了这些数字的适用范围）

| 项 | 值 |
| --- | --- |
| 机器 | 单台 Windows，压测客户端与被测服务**在同一台机器**上抢 CPU |
| JDK | Eclipse Temurin 17.0.20 |
| 应用 | Spring Boot 3.2.5，内嵌 Tomcat（默认线程数），Hikari 连接池 20 |
| MySQL | 本机 MySQL 8.0.46（3306），无容器 |
| Redis | 5.0.14 Windows 版（6380），单实例，无持久化 |
| 压测客户端 | Node 22 + `http.Agent({keepAlive:true})`，32 长连接 |

**所以这些数字只能横向比（开缓存 vs 关缓存），不能当“这个服务能扛 5000 QPS”的结论**：
同一台机器上客户端也要吃 CPU，而且 Windows 的调度抖动明显大于 Linux。

## 2. 方法（不写清楚方法的性能数字没有意义）

1. **预热**：每轮先发 1200 个请求，不计入统计。原因是 JIT —— 见第 5 节的实测证据，
   同一份代码冷启动跑出 1487 QPS，充分预热后是 5612 QPS，差 3.7 倍。
2. **每档跑 3 轮以上**，全部列在表里，不挑最好看的那一轮。
3. 延迟取单请求往返时间（含网络栈），QPS = 请求数 ÷ 墙钟时间。
4. 读场景：32 并发 × 6000 请求；写场景：3 并发（种子数据里只有 3 个学生账号）× 1200 请求。
5. 缓存开关通过 `--app.cache.enabled=false` 启动参数切换，**代码完全一致**。

## 4. 写路径：缓存是成本，不是收益

报名/取消循环（3 个用户反复报名→取消，抢同一条 `activity` 行的锁）：

| 配置 | QPS | P50 | P95 | P99 |
| --- | --- | --- | --- | --- |
| 缓存开 | 382 | 6.75ms | 14.76ms | 23.60ms |
| 缓存开 | 468 | 6.25ms | 7.92ms | 9.99ms |
| 缓存开 | 294 | 7.51ms | 35.20ms | 41.23ms |
| 缓存关 | 322 | 8.88ms | 12.44ms | 15.83ms |
| 缓存关 | 230 | 6.70ms | 36.51ms | 41.84ms |
| 缓存关 | 250 | 6.56ms | 36.31ms | 39.55ms |
| 缓存关 | 263 | 6.52ms | 36.85ms | 38.57ms |
| 缓存关 | 271 | 10.12ms | 15.75ms | 31.44ms |
| 缓存关 | 404 | 7.02ms | 9.61ms | 17.53ms |

**两组区间完全重叠**（294–468 vs 230–404），统计上分不出快慢 —— 所以不宣称任何结论。

但代码层面的事实是明确的：开缓存时每次写操作要多付两次 Redis 往返
（`DEL detail` + `INCR list:ver`），这是**纯成本**。它换来的是读路径的收益，
所以这道算术只有在读远多于写时才成立 —— 本项目是「一次报名、几十次浏览」，成立。

顺带发现：`off-run3` 那 1200 次里出现了 2 次 **409**。
循环模型的假设是「POST 与 DELETE 严格交替」，一旦某次请求的配对被打乱（例如连接复用下的重发），
就会出现「已报名却又报名」。409 正是防重复报名在起作用，不是数据被写坏：
JUnit 里 40 线程抢 5 名额的断言（恰好 5 成功、计数与记录严格相等）仍然全绿。

## 5. 压测方法本身踩的坑（这条比数字重要）

第一次跑缓存开：**1487 QPS**。同一份代码，先跑一轮再测：**4231 QPS**。再跑：**5095 / 5612**。

差的不是机器，是 **JIT**：前几千个请求里 C1/C2 还在编译热点方法，`ActivityPhase.resolve`、
Jackson 序列化、MyBatis 映射这些路径都还没编译成机器码。如果只跑一轮就下结论，
会得出「缓存只提升 13%」这种完全错误的判断（1487 vs 1315）。

所以压测脚本里预热是**必选**而不是可选项，而且第一轮统计要整轮丢弃。

## 6. Redis 挂了会怎样（真杀进程测的）

### 6.1 故障瞬间

Redis 不在时冷启动服务，**不做预热**，直接 32 并发打 1000 个请求：

| 指标 | 值 |
| --- | --- |
| 失败请求 | **0** |
| P50 | 28.75ms |
| P95 | 86.83ms |
| P99 | **1133.60ms** |
| max | 1190.24ms |

P99 落在 1.1 秒，正好等于 `spring.data.redis.timeout: 1s` ——
故障一开始，并发的那批请求各自撞了一次命令超时；之后 `degraded-cooldown` 生效，
10 秒内直接绕过缓存，延迟回落到查库水平（P50 28ms）。
**上限是被配置钉死的：没有这个 1s 超时，线程会跟着挂住的连接一直等下去。**

### 6.2 静默期内

| 指标 | 值 |
| --- | --- |
| 失败请求 | 0 |
| P50 | 13.34ms |
| P95 | 24.04ms |
| P99 | 33.27ms |

和「缓存关」那一档基本一样（P95 18–24ms），符合预期：降级路径就是查库。

### 6.3 日志没被刷爆

整个故障窗口里 `进入 10 秒降级期` 只打了 **1 条**。
如果每个请求都打一条，Redis 挂 1 分钟就能产出几万行日志，把真正有用的信息淹掉。

## 7. 压出来的两个真问题（已修）

### 问题一：Redis 一挂，`/actuator/health` 直接 503 —— 存活探针会把健康实例全部重启

```
Redis 正常：/actuator/health -> 200 {"status":"UP"}
Redis 挂掉：/actuator/health -> 503 {"status":"DOWN"}   ← 但业务接口仍然 200
```

业务明明还能跑（降级查库），健康检查却判死。如果 K8s 拿这个地址当 **liveness** 探针，
结果就是：Redis 抖一下 → 全部实例被判定死亡 → 重启 → 冷启动 → 更久连不上 Redis → 雪崩。

**修法**（`application.yml` + `SecurityConfig`）：

```
/actuator/health            -> 503 DOWN   综合状态，如实反映（该报警就报警）
/actuator/health/liveness   -> 200 UP     进程 + 数据库，不含 Redis
/actuator/health/readiness  -> 503 DOWN   依赖不齐，先别接流量
```

并且 `/actuator/health/**` 必须匿名可访问 —— 探针是编排系统发的，它没有令牌。
第一版只放行了 `/actuator/health`，结果两个子路径都被 401 拦住，探针永远失败。
Redis 恢复后三个端口全部回到 `200 UP`，已实测。

## 8. 复现

```bash
# 1) 起依赖（本机 MySQL 3306 / Redis 6380）
# 2) 起服务，注意 -Dfile.encoding=UTF-8，否则中文日志在 Windows 上是 GBK，grep 不到
java -Dfile.encoding=UTF-8 -Dsun.stdout.encoding=UTF-8 \
     -jar target/campus-club-backend-0.1.0-SNAPSHOT.jar --server.port=8090

# 3) 缓存开
bash bench/run-p7.sh cache-on

# 4) 关缓存重启后再跑一遍（对照）
java -jar target/campus-club-backend-0.1.0-SNAPSHOT.jar --server.port=8090 --app.cache.enabled=false
bash bench/run-p7.sh cache-off

# 5) 单条命令直接测某个接口
node bench/loadtest.js --mode=get --url=http://127.0.0.1:8090/api/activities/1 \
     --token=<jwt> --concurrency=32 --requests=6000 --warmup=1200
```

## 9. 这套数字不能证明什么（诚实边界）

- **不能证明生产容量**：单机、客户端与服务同机、Windows 调度、无网络延迟。
  真实的 P95 会包含网络与网关，通常比这里大一个量级。
- **写路径只有 3 并发**：受种子数据限制。写入的并发正确性由 JUnit（40 线程抢 5 名额）证明，
  而不是这一档压测。
- **没测长稳**：所有场景都在 5 秒内结束，没有观察 GC 长尾、内存增长、连接泄漏。
  真要上线，需要至少 30 分钟的持续压测并盯 `jvm.gc.pause`、连接池活跃数、慢 SQL 计数。
